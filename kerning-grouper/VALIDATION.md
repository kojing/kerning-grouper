## v0.5.5 お作法でまとめるグループ作成（2026-10-27）

OFL 20書体（クラスを使う書体）の欧文（A〜Z、a〜z、U+00C0〜024F の文字）。正解はプロのカーニングで相手と値の並びが同じ字（クラス定義は書き出しで分割されることがあるため動作で揃えた）。Web 版のエンジン（engine.js）で測定。

| 方式 | 後ろ側 F1 | 前側 F1 | 後ろ側 適合率 | 前側 適合率 | グループ数／プロ（後ろ / 前） |
|---|---|---|---|---|---|
| 形のみ（強さ0） | 0.087 | 0.043 | 91.5% | 87.1% | 4.05 / 3.87 |
| 形のみ（強さ40） | 0.262 | 0.296 | 71.6% | 71.6% | — |
| お作法オン（強さ0） | 0.767 | 0.703 | 88.0% | 89.7% | 1.33 / 1.49 |
| お作法オン（強さ40） | 0.780 | 0.746 | 85.0% | 85.9% | 0.93 / 1.09 |

方式の比較（Python で試作、同じ正解）：元の字のみ 0.435 / 0.653、＋定番の組 0.754 / 0.704、＋左右別の表 0.795 / 0.754、記号も比べた形の確認 0.137 / 0.072（記号の高さが違うため、ほぼまとまらない）。グループの切り方だけで生じるプロの値とのずれは、どの方式でも 3.3 以下（1000 UPM）。

かな：IBM Plex Sans JP で濁音・半濁音が元の字と同じグループなのは後ろ側（字の左）47/47、前側 0/46。エンジンでは後ろ側の適合率 100%、グループ 177 → 125。

## v0.5.6 VFM のグループ推定と往復（2026-10-27）
- グループ推定：OFL 20書体の GPOS クラスカーニングをグリフの組に展開し（FontLab の VFM と同じ形）、推定したグループを本来のクラスと比べた（eval/dump.py・eval/infer.py）。同じ値の並びだけ：F1 先頭 0.948・後ろ 0.955。個別例外を許す推定：0.964・0.969（適合率は同じ 0.975 / 0.984、再現率 0.928 → 0.955）。
- 往復：Adobe-Japan1-6 の明朝体（23,058 グリフ、FontLab 8 で書き出した VFM 7,808 ペア、クラス定義なし）。名前はすべて解決（コードポイントのないグリフ 109 を含む。CID・GSUB 機能で見つけた名前は metrics と照合して誤りなし）。「すべて引き継ぐ」＋「構成が変わったところだけ」で保存した VFM は、元と全ペア一致・metrics 一致。書体そのものは市販品なのでリポジトリには入れていない。
- アクセント付き欧文：上の書体で À/B は「その他」扱いで +100（和文の基準ペアの間隔）だったのが、大文字の組として −20（A/B と同じ）。
- サイドベアリングの調整（試作、採用せず）：かなだけで、しきい値以上のクラスの組 −19%（テスト書体）・−20%（明朝体）。字詰めオンでは −48%・−55%。初期設定で効果が小さいため外した。
- クラスの圧縮（欧文 62 字＋かな、欧文と和文の基準ペア、強さ 0）：許容差だけで「全列が許容差内」の合併に限ると、クラスはほぼ減らなかった（211 → 209）。行は少数の列だけが大きく違うことが多いため、違う組を個別例外に残して合併する方式にした。推定容量 テスト書体 / 明朝体：なし 65,592 / 75,168、許容差 10：40,320 / 45,672、＋刻み 5：38,402 / 43,536、＋刻み 10：37,668 / 41,850、刻み 15：58,758 / 50,710、刻み 20：44,598 / 53,524、許容差 20・刻み 10：25,316 / 30,748、許容差 30・刻み 10：18,932 / 22,538。光学モデルの誤差はどれも ±1% 以内。
- クラスの圧縮・安全規則の追加後（生成していない組のあるクラスはまとめない、0 と非0 は入れ替えない）：テスト書体 / 明朝体 許容差 10：46,824 / 45,402、＋刻み 10：38,512 / 42,268、許容差 20・刻み 10：32,630 / 36,138、許容差 30・刻み 10：29,342 / 33,744。最初の版は、欧文と和文のように別の領域でカーニングする行を合併でき（生成していない組の値が入る）、テスト書体の数字はその分だけ小さく出ていた。
- 欧文＋ギリシャ＋記号（Fira Sans、OFL）：252 字（ASCII・Latin-1 の文字・ギリシャ基本・記号）で、プロの値との平均の絶対差（どちらかが0でない組）：欧文×欧文 16.2、ギリシャ×ギリシャ 19.2（変更前 23.3）、ギリシャ×欧文 18.1（21.1）、記号を含む組 24〜44。グループのプロの挙動グループとの一致 F1：先頭 0.44・後ろ 0.56（適合率 0.85 / 0.92、再現率が低い：プロは大きなグループ）。UI で 565 字（ギリシャ拡張を含む）を最後まで実行：エラーなし、推定容量 103.9 KiB（許容差 10）。
- 優先度モデル（20 書体、ASCII＋主な引用符・ダッシュ 110 字、各 12,100 組、プロが値 10 以上を入れた組を「入れる」）：書体ごとに1本ずつ外して学習・評価（leave-one-font-out）。AUC 0.797（書体別 0.72〜0.94）。プロが入れる組は全体の 11%。「入れる組」の当て方：これまでのツール（|値|≥20）は 29.8% の組に入れて適合率 0.20・再現率 0.53・F1 0.29。優先度 30% 以上：10.4% の組に入れて適合率 0.45・再現率 0.41・F1 0.43。40%：0.50 / 0.34 / 0.40。50%：0.55 / 0.27 / 0.36。
- 優先度 30% をツールに入れたとき（学習に含まれる 6 書体、94 字）：入れる組の割合はプロに近づき（例 Inter 43.6% → 10.9%、PT Sans 35.4% → 7.5%）、入れた組のうちプロも入れている割合は 13〜49% → 50〜85%。プロだけが入れる組（AO・Po・fo など）は、ツールが値を出さないので優先度では増えない。
- 全分類の 720 字では、和文（かな・約物・全角）の組は優先度の対象外で、値の入る組 75,736 が容量の大半を占める。
- 容量（許容差 10）：優先度はクラスをまとめた後、書き出すクラスの組ごとに決める（まとめる前に字の組ごとに 0 にすると、まばらな 0 を残すための個別例外が増えて容量がかえって増えた：Fira 45.9→51.9 KB）。Fira Sans サブセット 275 字：優先度なし 45.9 KB → 30% で 33.8 KB（64 KB 以内）。全分類 720 字：195.1 → 164.3 KB（許容差 20・刻み 10 で 133.1 KB）。
