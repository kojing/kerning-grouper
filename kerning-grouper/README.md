# Kerning Grouper v0.5

FontLab 8向けの左右別カーニンググループ候補作成ツール。左右の形状分類と、グループ間の光学カーニング生成に対応します。VFM入出力・GPOS互換性検査は含みません。

## 最短の試し方

ZIPを解凍し、`standalone.html`をChromeまたはEdgeで開きます。同じフォルダーの`kerning-grouper.js`が必要です。フォントを選択し「グループを作成」を押します。外部通信・フォントのアップロードは行いません。

## Confluenceへの設置

1. `kerning-grouper.js`を社内で配信できる場所に配置します。
2. `confluence-macro.html`の`MAIN_JS_URL`を、そのJSの実URLへ変更します。
3. ConfluenceのHTMLマクロ本文に、HTMLファイルの内容を貼り付けます。
4. ページを表示し、OTFの読込・解析・JSONのダウンロードを確認します。

メインJSにはOTFパーサー・UI・解析エンジン・Workerを同梱済みです。実行時のnpm、ビルド、CDNは不要です。`src`とビルド関連ファイルは改修用です。

添付ファイルURLがHTML/JSとして実行できるかはConfluence構成次第です。強制ダウンロード、CSP、MIMEタイプ、権限により読込が拒否される場合は、管理者が許可した社内静的配信先を使ってください。制約を回避するための設定変更は行いません。

HTMLマクロ内のインラインスクリプト、メインJSの取得、インラインスタイルが許可される必要があります。`blob:` Workerが禁止される場合はUIスレッドの分割実行に切り替わります。Shadow DOMでスタイルを隔離し、各ルートに独立した状態を持ちます。

実際の社内Confluenceにはアクセスしていません。マクロ製品によるスクリプト実行方式、CSP、サンドボックス、ファイル選択・ダウンロードの可否は設置先で確認してください。

## 操作

- OTF/TTF読込後、対象カテゴリ・個別グリフを選択します。既定はASCII英数字です。
- 左輪郭はペア後ろ側、右輪郭はペア先頭側として独立分類します。
- スライダー変更後、約350msで再計算します。前回結果は「条件変更あり」と表示します。
- グループをクリックすると輪郭・原点・送り幅・輪郭プロファイルを重ね表示します。
- 複数グループをチェックして統合すると固定されます。閾値超過は詳細に赤く表示します。
- メンバーのボタンを選択して分離すると、各文字を単独グループにして固定します。
- 「固定を全解除」は現在表示している側のみ解除して再分類します。
- 判定単位は1,000 UPM基準です。形状RMSと一定の余白ずれ、元座標での最大差、高さの不一致を別々に評価します。
- 初期閾値は実用評価のための仮値です。特にアクセントや細部は精密設定でも確認してください。
- 設定（判定条件・カーニングの設定・対象の字・領域の組み合わせ・容量予算）はブラウザに自動で保存され、次に開いたときもそのまま使います（v0.5.6）。
- グループとカーニングは「6 保存」の VFM で FontLab とやり取りします。途中から続けるときは、その VFM を「1 対象」で読み込みます。

## 対応範囲

- 静的・単色・横組み用の通常アウトライン（CFF1 / TrueType）。複合TrueTypeグリフの解決はopentype.jsに委譲します。
- 可変フォント・CFF2・カラーフォント・TTCは未対応。
- 空輪郭・ゼロ送り幅・結合マーク・空白・制御文字・.notdefは対象外。
- 1回の解析は800グリフまで。フォント全体65,535グリフ以下（Adobe-Japan1-6 の 23,058 グリフも可）、ファイル60MB以下。
- Latin拡張プリセットはU+00C0–024F、U+1E00–1EFFの範囲です。
- 個別選択一覧は検索結果の先頭200件。表示上の輪郭重ねは先頭100メンバーまで。
- 一様な高さサンプリングなので、サンプル間の微小形状や極端に薄い輪郭の検出は保証しません。比較可能な高さが3未満なら自動統合しません。
- アウトラインは非ゼロワインディングで処理し、約0.35 units以下を目標にベジェを線分化します。
- フォント照合は利用可能ならSHA-256、非セキュアな社内HTTPでは弱いチェックサムにフォールバックします。後者は暗号学的同一性を保証しません。

## 容量表示について

64 KiB = 65,536 bytesを初期予算にします。予算は変更可能です。

カーニング生成後は、FontLab が書き出す kern ルックアップの大きさを計算します（v0.5.7）。FontLab は AFDKO と同じコンパイラで、クラスのカーニングを次の形にします：

- 1 つのルックアップに、グリフどうしのペア（個別の値、0 を含む）を PairPos Format 1、クラスのペアを Format 2 で 1 つ。
- Format 2 の行列は、値の入るクラスの組を持つクラスだけ（先頭 C1 × 後ろ C2＋1）× 2 bytes。
- Coverage と ClassDef は 2 つのサブテーブルの後ろにまとめて置かれます。

最初のサブテーブルからのオフセットがルックアップ全体に届くので、Extension Lookup を使わない限り、ルックアップ全体を 65,535 bytes 以内に収める必要があります。サブテーブルやルックアップを和文・欧文で分けても、この上限は変わりません（ゼロの行列セルが減るぶんだけ小さくなります）。makeotf（AFDKO 5.0.1）で書き出したフォントと比べ、0.1% 以内で一致しました（VALIDATION.md）。

カーニング生成前は、全グループの密な行列（Format 2）による上限の目安を出します。横組み・xAdvance のみで、ほかの GPOS 機能は含みません。

## 開発

Node.js 20以降で `npm ci` → `npm run build`。
`npm test`で輪郭・余白・クラスタリング・実OTFテストを実行します。実OTFテストは`TEST_FONT`環境変数でファイルを指定できます。

- `src/core.js`: 輪郭線分化、ワインディング、プロファイル、比較、complete-link分類、概算
- `src/engine.js`: 解析キャッシュ、進捗、中止
- `src/worker.js`: Workerインターフェイス
- `src/app.js`: UI・入出力・手動編集

依存ライブラリのライセンスは`THIRD-PARTY-LICENSES.txt`を参照してください。ライブラリは配布物にバンドルされています。

# v0.2: グループ・光学カーニング

## 新しい操作

グループ作成後、画面下の「グループ間のカーニング」で基準ペアと条件を調整し、「カーニング生成」を押します。

- 光学判定の比重：0%は水平最短距離主体、100%は3尺度の光学余白主体。両方で最小余白の保護が働きます。
- 基準からの間隔調整：基準ペアのモデル余白に加算。正は広め、負は詰め気味。
- 最小余白：輪郭プロファイルの拡張に使う保護距離。
- 自動補正の上限：過度の補正を制限。安全上必要な正の補正は上限より優先し、警告します。
- 微小値の省略：小さな自動補正を省きます。手動値と安全に必要な値は保持します。
- クラス共通化の許容差：グループ中央値と個別推奨値の差が大きいものを例外にします。
- 数字×数字を保護：値0を維持。保護した結果、最小余白を満たさないものは警告します。

クラス値・個別ペア値は手動指定可能です。クラス値を変更しても接触回避・数字保護・手動ペアを優先します。手動ペアの値が安全下限を下回る場合は、下限へ補正します。

基準ペアには、対象として選択している2文字を空白区切りで指定してください。大文字同士、小文字同士、大→小、小→大を分けて校正し、該当する基準がなければ有効な基準全体へフォールバックします。基準が1つもない場合は生成しません。

## 計算の内容

各文字の左右輪郭を2 unitsごとにサンプリングします。外向きの輪郭距離を指数関数の濃度場へ変換し、縦方向にGaussianぼかしをかけて隣接する2文字の相互作用を測ります。横24/60/120 units、縦18/45/90 unitsの3尺度を重み0.2/0.5/0.3で評価します。

この評価の余白と、基準ペアの余白の差から最適補正を求めます。最短距離側の補正と比重スライダーで混合し、最小余白と補正上限を適用します。グループの全メンバー組み合わせを評価し、中央値をクラス値にします。共通化の許容差や保護条件に合わないものは個別例外にします。

これは**試作の光学ヒューリスティック**です。人間が自然と感じる間隔を保証するものではありません。内部のモデル誤差が減ることと、実際の読みやすさは同一ではありません。複数文字のリズム、単語の形、印刷サイズ、ヒンティング、内部カウンター全体の黒みは十分に扱っていません。補正前後の文字列・ぼかし表示で校正してください。

最小余白判定もサンプリング近似です。微小形状やサンプル間の衝突の完全保証はありません。生成の上限は800グリフ（最大640,000ペア）です（v0.5.6 で 320 から引き上げ）。

## 保存と容量

- 作業JSONの保存・復元は v0.5.6 で廃止しました。設定はブラウザ（localStorage）、グループとカーニングは VFM です。
- FontLab 用 VFM：FontLab 8 のメトリクスファイル（.vfm）。クラスをグリフ単位のペアに展開し、フォントの単位で書きます（v0.5.3、下記）。
- ペアCSV：補正あり・例外・警告のあるペアを保存します。
- CSV には1,000 UPM基準と元フォント単位の値を併記します。グリフ名は VFM と同じ FontLab の名前です。
- 出力値は既存カーニングに追加する値ではなく、置き換え用の最終値です。
- 容量概算には個別例外の概算を追加します。行列中の値を0にしても行列自体は小さくなりません。最終容量・16bitオフセット・Extension Lookup非使用は保証しません。

今回の版では、カーニング生成中にグループを変更すると計算を中止し、古いカーニングを無効にします。光学条件変更時も再生成が必要です。微小値の省略とクラス共通化の許容差のみ、計算済み結果から即時反映できます。

## v0.4 統合の強さ

「統合の強さ」0〜100を追加。0は従来の判定。強くすると分類に使う左右輪郭だけをGaussian平滑化（最大σ48 units）し、形状・余白・局所差・高さ不一致の許容値を連続的に拡張します。各実効許容値を表示します。グループ全員の組み合わせが条件内である完全連結方式を維持しています。手動固定グループはそのまま保持します。

輪郭自体やフォントは変更しません。カーニング生成と接触回避は元輪郭で計算するため、不適合な組み合わせは個別例外に分かれます。強くまとめても総容量が小さくなるとは限りません。分類後、必ずカーニングを再生成し、例外込みの容量を確認してください。強度の変更で既存カーニングの手動調整も無効になります。

Noto Sans JP由来・かなと約物174文字での測定（他の条件は初期値）：

|統合強度|先頭グループ|後ろグループ|個別例外|例外込み概算 bytes|
|---|---:|---:|---:|---:|
|0|174|172|0|63142|
|40|162|147|201|52354|
|70|134|123|3807|52310|
|100|87|83|11432|64120|

デモ初期強度は40、通常アプリは互換性のため0です。旧作業JSONでは強度を0として復元します。詳細は samples/grouping-comparison.json、再実行は npm run test:grouping。

平滑化と許容差による候補分類であり、全ペアの光学的挙動からグループを最適化する機能ではありません。見た目の適否、実OTF容量は未保証です。

### 和文の字詰め・約物（kern に含める）
「4 カーニング生成」の「和文の字詰め・約物」で、字詰めと約物の詰めを kern の値として作れます（palt・chws は使いません。既定はオフ）。
- 値の内訳：kern ＝ 字詰め ＋ 約物 ＋ 光学補正。「5 カーニング調整」の選択中のペアに内訳を表示します。
- 字詰め（ツメ組み）：かなの左右を、基準ペアでそろえた間隔からさらに詰めます。「詰めの強さ」（1組あたり左右合計、既定60）×字種ごとの割合（ひらがな100%・カタカナ110%・小書き仮名130%、長音はカタカナの7割）。小書き仮名は左側を強く、右側を控えめに詰めます。字面が触れない最小余白（「最小余白」の半分ずつ）は守ります。漢字・欧文・数字は詰めません。
- 約物の規則：約物（始め括弧・終わり括弧・読点・句点・中点、全角のもの）を含む組は、光学補正ではなく規則で決めます。全角の枠のうち空いている半分（中点は四分ずつ）を詰め、残す空きは方針で決まります。
  - ツメ組み（既定）：残す空きを数値で調整できます。句点の後（既定500＝二分）、読点の後（250＝四分）、括弧の外側（0）、中点の前後（250）。0〜500（中点は0〜250）。
  - 残す空きを変えたときは、約物の組だけその場で再計算します（再生成は不要）。
  - ベタ組み基準（JLREQ）：約物の外側に二分を残す。
  - 約物どうしは0（」「・、「 は二分）。空いている側は字面の位置から判定し、位置が想定と違う約物は「要確認：punct-position」にします。
  - 規則の値がクラス値と許容差以上ずれる組は、個別例外の自動作成がオフでも個別例外にします（理由「約物の規則」）。
- グループ：約物は JLREQ の種類が違えば同じグループに入れません（グループ作成時に常に適用）。

### ペアの表
- 「グループ単位」：1セル＝グループ同士の組（クラス）。代表グリフを元輪郭で描き、生成後はクラス共通値で色分け・値表示します。個別例外を含むクラスには黄色の点が付きます。
- 「グリフ単位」：1セル＝グリフ同士の組。ペアごとの最終値（例外込み）を表示し、個別例外は黄色枠、グループの境目は太線です。
- 文字での絞り込み：スペースを含めると OR（行か列のどちらかが一致する組を表示。一致した行・列を先頭に並べ、左上＝両方一致、上の帯＝先頭が一致、左の帯＝後ろが一致、どちらにも当たらないセルは空白）、スペースなしは AND（一致した行と一致した列の組だけを表示）。1文字だけのときは OR（その字を先頭にした組と後ろにした組の両方）。例：「AV」は A・V 同士の組だけ、「A V」は A か V を含む組すべて。凡例に一致した行・列の数とモードを出します。
- 共通の操作：セル14〜96px（28px未満は字形を省いて色だけの一覧）、並び（グループ順・グリフ数・補正量）、「生成値を適用」の切り替え、ツールチップ、矢印キー移動。
- セルを選ぶと、「5 カーニング調整」タブにそのクラスの全メンバーの組み合わせ（最大24×24）を表示します。その中のペアをクリックすると、ペアの前後比較・クラス値・個別値の手動指定に切り替わります。タブ側で組やグリフを変えると表の選択も追従します。
- 行・列の見出しを選ぶと、「3 グループ調整」タブにそのグループの輪郭の重ね表示・メンバー・判定指標を表示し、分離・固定ができます。統合の対象は一覧でチェックしたグループだけです（表示中のグループや統合直後のグループは、チェックしない限り含みません）。表の見出しをCtrl・⌘・Shiftを押しながら選ぶとチェックの付け外しになり、最初の1回は表示中のグループにもチェックが付きます。2つ以上チェックすると「チェックした n グループを統合」が使えます。統合するとチェックは外れます。
- 描画は表示範囲だけです。実機・Confluence上での性能は未検証です。

### 既定値：領域の組み合わせ・個別例外
**領域ごとの組み合わせ（既定：欧文同士・和文同士のみ）**　「1 対象グリフ」の表で、ペアの先頭の領域（行）×後ろの領域（列）ごとに、カーニングするかをチェックで決めます。領域は、そのグリフが当てはまるUnicodeの規則のうち、チェックしている最初のものです（表には対象に含まれる領域だけが出ます）。既定では欧文の規則同士・和文の規則同士をカーニングし、欧文×和文はカーニングしません。既定から変えたマスは黄色い枠で示し、「すべてカーニング」「既定に戻す」で一括変更できます。

- カーニングしない組み合わせのペアは評価せず値0にします。表では斜線で表示し、その組の手動指定はできません。
- カーニングしない相手が違う文字同士は、同じグループにしません（手動統合も不可）。クラスの値はクラスの全員に掛かるため、混ぜると0にすべきペアへ値が漏れるからです。たとえば「和文約物→ひらがな」だけを外すと、和文約物は他の和文と別の先頭グループに、ひらがなは別の後ろグループに分かれます。
- 容量の概算は単一PairPos Format 2の密な行列のままで、行列分は変わりません（グループが分かれる分は増えます）。和欧間などの追加余白の指定は未実装です。
- 作業JSONに regionAllow（既定から変えた組み合わせ）を保存します。以前の作業JSONは、mixScripts=false なら既定、それ以外（v0.4以前を含む）はすべての組み合わせをカーニングする設定で復元します。

**グループ内の文字ごとの個別例外（既定オフ）**　生成バーの「グループ内の文字ごとの個別例外を自動で作る」。オフではクラス値だけで生成します。
- 光学的な個別例外（クラス値から「クラス共通化の許容差」以上ずれるペア）は作りません。許容差スライダーは無効になります。
- 接触回避は維持します。接触しそうなメンバーを含むクラスは、個別例外ではなくクラス値を引き上げて回避します（引き上げた組の数を要約に表示）。
- 手動の個別値と数字保護は、明示的な指定として有効です（これらは個別例外として残ります）。
- 切り替えは再生成なしで即時に反映されます。

同梱の和文サンプル（かな・約物174字、他は初期値）での比較（容量はモデル概算、誤差は光学モデル内の値で見た目の保証ではありません）：

|統合強度|グループ（先頭/後ろ）|個別例外オン：例外 / bytes / 誤差|既定（オフ）：例外 / bytes / 誤差 / 引き上げ|
|---|---|---|---|
|0|174 / 172|0 / 63142 / 99.3|0 / 63142 / 99.3 / 0|
|40|162 / 147|201 / 52354 / 99.4|0 / 50840 / 99.4 / 0|
|70|134 / 123|3807 / 52310 / 99.5|0 / 36072 / 100.3 / 6|
|100|87 / 83|11432 / 64120 / 99.5|0 / 17376 / 104.2 / 190|

既定では、統合を強めるほど容量が減ります。その分、クラスの代表値からずれるペアの誤差は個別には補正されません。強い統合では「文字列で校正」とグリフ単位の表で確認してください。

作業JSON：mixScripts と kerning.settings.exceptions を保存します。旧JSON（v0.4〜v0.5途中）は、どちらも当時の動作（オン）で復元します。容量の概算は単一PairPos Format 2の密な行列で、和欧の設定で行列分は変わりません。和欧間の追加余白は未実装です。

### 補正前後の重ね表示
- 校正のプレビューは入力欄を持たず、プレビューをクリックするとその位置にカーソルが出て、そのまま入力できます（日本語入力・選択・コピー＆ペースト可、Enter で改行して複数行を比較）。行ごとに補正の値と「行の長さ」を表示します。
- 校正のプレビューは「−／全体／＋」で拡大縮小できます（50〜800%、Ctrl／⌘＋ホイールでも可。カーソル位置を中心に拡大）。「全体」は行全体を幅に合わせ、拡大中は横スクロールで送ります。
- 校正のプレビューは1行に重ねて表示します。輪郭が補正前、塗りが補正後で、各文字の下のバーが補正前からのずれです（暖色＝詰めた、寒色＝開けた、数値は1000 UPM換算）。右上に行全体の長さの変化を表示します。
- 画面上の説明文（プレビュー下の凡例、表の「行＝ペアの先頭…／値はクラス共通値」、キャンバス内の「輪郭＝補正前…」、フッターの版表記）は表示を簡潔にするため削除しました。見方はこの節を参照してください。
- 各文字の「補正前」は、その字の直前のペアの値だけを戻した位置です（ペアごとのずれが読める）。行全体の長さの変化は右上の数値で確認します。
- プレビュー右上と表のツールバーの「カーニングの表示のみ」をオンにすると、補正前の輪郭・ずれのバー・数値（表ではセルの色分けも）をまとめて消し、補正後の文字だけを表示します（プレビューと表は別々に切替、既定オフ）。表の「値のヒートマップ」切替はこのチェックにまとめました。
- 表のセル（グループ単位・グリフ単位）と、調整タブのクラス内全ペア・選択ペアの比較も、同じ重ね表示です。セルの拡大率と位置は補正前の並びで固定するため、詰めたペアは文字が重なるように、開けたペアは離れるように見えます（以前はセルに合わせて拡大縮小していたため、補正の差が見えにくくなっていました）。

### 上限に張り付く組（約物など）
全角の句読点・括弧などは、字面の外の空きを光学モデルが「大きな隙間」と判定し、後ろに何が来ても「自動補正の上限」（初期値100。v0.5.0までは240）まで詰める値になりがちです。既定では、上限に達した組も上限の値で動かします。もっと動かしたい場合は「自動補正の上限」を上げてください（数値欄は1000まで入力可）。

「4 カーニング生成」の「上限に張り付く組（全角の約物など）は0にする」をオンにすると、クラス内の全ペアが上限に達した組を0にします（既定オフ、再生成なしで即時反映）。0になったグループは全ペア0のグループとしてクラス表から外れます。和文サンプル（174字、強度40、他は初期値）では、先頭5・後ろ4グループ（。、」』）と「『（！）が外れ、容量の概算は50,840→48,032 bytesでした。

### スライダーの自由入力
各スライダー横の数値欄には、スライダーの範囲を超える値も入力できます。範囲外の値を入れると、スライダーは端に寄せて表示し、「スライダーの範囲外」と表示します。数値欄で受け付ける範囲は、値の意味と計算量から決めた次の上限までです（超えた場合は上限に合わせ、理由を表示します）。

|項目|スライダー|入力できる範囲|理由|
|---|---|---|---|
|統合の強さ|0〜100|0〜200|平滑化の幅が文字の高さに近づき分類の意味が薄れるため|
|輪郭形状の許容差|0〜60|0〜500||
|余白の許容差|0〜80|0〜500||
|局所差の許容値|0〜120|0〜1000||
|高さの不一致率|0〜0.5|0〜1|割合のため|
|光学判定の比重|0〜100|0〜100|機械判定との配分の割合のため|
|基準からの間隔調整|−80〜100|−500〜500|1/2 emを超える一律調整は想定外|
|最小余白|0〜60|0〜200|接触判定の計算量が急増するため|
|自動補正の上限|20〜500|0〜1000|1 emを超える補正は想定外|
|微小値の省略|0〜50|0〜1000||
|クラス共通化の許容差|0〜80|0〜1000||

和文サンプル（174字、初期値、個別例外オフ）では、統合の強さ150で41×41グループ・約6.1KB、200で26×24グループ・約3.9KBの概算でした（接触回避でクラス値を引き上げた組がそれぞれ300・231）。強すぎる統合は形の違う文字を同じクラスにするため、目視確認が必要です。作業JSONの検証も同じ範囲で行います。

### 全ペア0のグループの除外
「微小値の省略」などの結果、最終値（個別例外を含む）がすべて0になったグループは、クラス表から除外して扱います。OpenTypeのクラスカーニングでは、先頭側のこうしたグループは対象（Coverage）から外せ、後ろ側は何もしないクラス（class 0）にまとめられるためです。容量の概算はその分を差し引き、要約に「全ペア0のため除外：先頭 n・後ろ n グループ」と表示します。表では、カーニングに含まれないグループの行・列を、見出しからセルまで斜線と薄い文字で無効表示にします（カーニングしない領域の組み合わせのセルと同じ表示）。見出しには「除外」と出ます。（v0.5.2 までのカーニングJSONでは excludedGroups として番号を書き出していました。VFM はペア単位なので該当ペアは書きません。）0でない個別例外（手動の個別値など）が1つでも残るグループは除外しません。同梱の和文サンプル（174字）と欧文ASCIIでは、微小値の省略を5〜30にしても該当グループは0件でした。

### 対象グリフ＝Unicodeの規則 − 除外する文字
「1 対象グリフ」では、Unicodeの一般カテゴリ（Lu・Ll・Nd・P・S など）、用字系（Script=Latin・Hiragana・Han など）、ブロックの範囲で決めた規則ごとのチェックで、含める文字を選びます。各チェックの横には、読み込んだフォントに実際にある字数を表示します（0字の規則は薄く表示）。

|区分|規則|内容|
|---|---|---|
|欧文|英大文字 A–Z|基本ラテン（U+0000–007F）· Lu|
||英小文字 a–z|基本ラテン · Ll|
||数字 0–9|基本ラテン · Nd|
||ASCII 記号・句読点|基本ラテン · P / S|
||ラテン文字（拡張・アクセント付き）|Script=Latin · L · U+0080以降（全角を除く）|
||ギリシャ・キリル文字|Script=Greek / Cyrillic · L|
||その他の記号・句読点|P / S · U+0080–U+2FFF|
|和文|ひらがな|Script=Hiragana ＋ U+3040–309F|
||カタカナ（長音・中黒を含む）|Script=Katakana ＋ U+30A0–30FF・31F0–31FF・半角 FF66–FF9F|
||和文の約物|U+3000–303F ＋ 全角・半角形の P / S（々〆などもここ）|
||全角英数|U+FF10–FF19・FF21–FF3A・FF41–FF5A|
||漢字|Script=Han|

対象は、チェックした規則のどれかに当てはまるグリフから、「除外する文字」に入力した文字を除いたものです（重複・空白・改行は無視、0.3秒後に反映して自動で再分類）。選択欄に「規則に該当 n − 除外 m」と内訳を表示し、除外欄の下に、範囲外で影響のない文字と、フォントに未収録の文字を表示します。ひらがな・カタカナ・和文の約物の3規則を選ぶと、同梱サンプルではちょうど174字（かな・約物）になります。漢字は数が多いので、1回の分類800グリフ・カーニング生成320グリフの上限に注意してください。

作業JSONには selection（version 2：rules と exclude）を保存します。以前の形式（範囲のチェック＋追加文字、または個別指定）は、保存されていた対象グリフを含む規則をすべてチェックし、それ以外を除外文字にする形で変換します。規則で表せないグリフ（文字コードのないものなど）は対象から外し、グループを作り直して通知します。

### グループ設定とカーニング生成の整合
- 生成できない状態では「カーニング生成」を押せなくし、理由を表示します（グループ未作成、条件変更後の未再作成、対象が800グリフ超、有効な基準ペアが0組）。
- 基準ペアは入力のたびに、有効な組数と対象にない組を表示します。専用の基準がない種類（大文字・小文字・大小混在・その他）は、他の基準の中央値で校正することを明示します。和文と欧文を両方選んで基準が初期値なら、欧文＋和文の基準を併用します。
- 対象に数字がないときは「数字×数字を保護」を無効にします。
- 左の「5 カーニング調整」タブのグループ・グリフ選択は文字で表示します（文字コードのないグリフはグリフ名）。

## v0.5.1 初期値の見直し（プロのフォントとの比較から）

OFL の欧文12書体（Source Sans 3、Lato、Fira Sans、PT Sans、Work Sans、Montserrat、Inter、Noto Sans JP、IBM Plex Sans JP、M PLUS 1p、Zen Kaku Gothic New、Kiwi Maru）の英字52字・全3.2万ペアで、生成結果をフォントに入っているプロの kern 値と比べ、次の2点を変えました。

1. **基準ペアと同じくらいの字間は動かさない**（`keepSpacing`、既定オン、「4 カーニング生成」のスイッチ）。基準ペアどうしの空きのばらつき（基準ペアそれぞれを目標と比べたときの補正量の最小〜最大）を「範囲」とし、範囲に収まる組は0のまま、外れる組だけを範囲の端まで補正します。基準ペア（HH・OO・nn など）は必ず0になります。字詰め・約物の規則は範囲の外側で、従来どおり足されます。
2. **初期値**：光学判定の比重 85→60%、自動補正の上限 240→100、微小値の省略 5→20。

| | 全ペアの誤差 | プロが詰めているペアの誤差 | プロが0のペアに値を入れる率 | 値を入れるペアの割合 |
|---|---|---|---|---|
| v0.5.0 初期設定 | 29.5 | 49.8 | 49% | 87% |
| v0.5.1 初期設定 | 8.9 | 26.4 | 12% | 19% |
| 参考：プロの値を入れているペア | | | | 24% |

（単位は 1000 UPM。18px 表示で 28 が半ピクセル。プロが詰めているペア＝プロの値の絶対値が20以上。）

かな（Noto Sans JP・IBM Plex Sans JP、palt と kern を合わせた空き方と比較、字詰めオン）でも誤差が 96〜113 から 32〜38 に下がりました。

旧作業JSONは `keepSpacing` がないため、当時の動作（オフ）で復元します。保存済みの光学比重・上限・省略値もそのまま使います。評価の詳細は VALIDATION.md。


## v0.5.2 学習した値の補正（欧文）

英字どうしのペア（大文字・小文字の4種類）で、ツールが値を入れると決めたペアの**値の大きさ**を、プロのフォントから学習したモデルで決めます。どのペアに値を入れるかは今までどおりです。「4 カーニング生成」の「欧文の値をプロのフォントから学習した補正で決める」（`learned`、既定オン）で切り替えられます。ペアの詳細には「学習補正：計算値 → 学習値」が出ます。

- **モデル**：勾配ブースティングの決定木100本（`src/kern-model.js`、約85KB、数値のみで字形は含まない）。学習元は OFL の12書体（v0.5.1 の評価と同じ）。
- **入力（116個）**：今の計算の値と内訳、文字の高さごとの空き（キャップハイトの −30%〜130% を 5% 刻み）、前の字の右側・後ろの字の左側の輪郭の位置、x ハイト／キャップハイトの比。入力は常に固定の基準設定（光学60%・上限100・基準ペアの範囲あり）で計算するので、スライダーを動かしてもモデルが見る値は変わりません。値の上限と接触回避は、ユーザーの設定をそのまま後から適用します。
- **キャップハイト・x ハイト**：フォントの H・x から求めます（選択していなくてもよい）。なければ OS/2、それもなければ 700・500。
- **精度**：学習に使っていない OFL の9書体（Barlow、DM Sans、Karla、Manrope、Noto Sans、Nunito、Public Sans、Raleway、Rubik）で、Web 版の処理を最後（グループ・クラス値）まで通して比べた結果：

| 補正なし（v0.5.1） | 25.9 | 62% | 11% | −23.6 |
| 補正あり（v0.5.2） | 14.4 | 87% | 1% | −1.7 |

  全ペアでも誤差 8.8 → 6.6。書体別では9書体中8書体で改善、Rubik のみ 14.4 → 16.9。

## v0.5.3 FontLab 用 VFM の書き出し

「6 保存」の書き出しを、本ツール専用のカーニングJSONから **FontLab 8 のメトリクスファイル（.vfm）** に置き換えました。FontLab の File > Import > Metrics で読み込みます。

**VFM の構造**（FontLab 8 が書き出した実ファイルで確認）

```
{ "dataType": "com.fontlab.metrics",
  "masters": { "<マスター名>": { "pairs": { "<前のグリフ名>": { "<後ろのグリフ名>": "<値>" } } } },
  "metrics": { "<グリフ名>": { "layers": { "<マスター名>": { "lsb", "rsb", "width", "xmin", "xmax", "ymin", "ymax" } } } },
  "upm": 1000 }
```

- 値は文字列で、フォントの単位です。本ツールの 1000 UPM の値を換算して整数に丸めます。0 のペアは書きません。
- カーニングはグリフ単位のペアです（クラスは展開）。CID フォントでは FontLab 自身もこの形で書き出します。
- `metrics` は任意です。読み込み先の VFM を選ばないときは書きません（字幅・サイドベアリングは変えない）。

**グリフ名**

- フォントがグリフ名を持つとき（名前付き CFF、TrueType の post 2）：その名前。
- 持たないとき（CID フォント、post 3）：FontLab がコードポイントから付ける名前。複数のコードポイントを持つグリフはいちばん小さいコードポイントで、`src/fontlab-names.js` の表（AGL for New Fonts を FontLab の実際の命名に合わせて補正）にあればその名前、なければ `uniXXXX`（BMP 外は `uXXXXX`）。FOT-マティス ProN M の OTF と、FontLab が書き出した VFM で、コードポイントのある 9,739 グリフすべての名前と送り幅が一致することを確認しました。

**読み込み先の VFM（任意）**

読み込み先のフォントから File > Export > Metrics で書き出した VFM を選ぶと、
- マスター名をその VFM から取り、
- 対象の字の名前がその VFM にあるかを表示し（ない名前は、送り幅と外接矩形が一致するグリフを探します）、
- そのファイルの、選んだマスターのカーニングだけを差し替えた VFM を作ります（メトリクスと他のマスターはそのまま）。

マスター名は、選ばないときはフォントの name ID 17（なければ 2）です。FontLab では、置き換える前に今あるカーニングを消すか、読み込み時に置き換えを選んでください（値は足し算ではなく最終値です）。


## v0.5.4 VFM からの読み込み（カーニングとグループ）

「1 対象」の「FontLab の VFM から始める」で、フォントを開いたあとに同じフォントから書き出した VFM を読み込みます。

- **カーニング**：選んだマスターのペアを読み込みます（フォント単位 → 1000 UPM）。グリフ名は書き出しと同じ規則でフォントのグリフに対応させ、合わない名前は VFM の字幅と外接矩形で探します。
- **グループ**：VFM にクラスの定義があればそれを使います（形式は未確認のため、`kerningClasses`／`classes`／`groups` の配列・辞書と `@名前` の参照を受け付けます）。なければ、**同じ相手に同じ値が並ぶグリフ**を同じグループとして推定します（前側は行、後ろ側は列）。
- **対象**：VFM でカーニングされている字を対象にします（Unicode の規則＋除外で表します）。コードポイントのないグリフ（.ital などの切り替え字形）は対象にできません。それらを含むペアは書き出しでそのまま残します。

**グループの作り方**（「2 作成」の「VFM のグループ」）

| 選択 | 動き |
|---|---|
| 1字のグループと、グループに入っていない字だけ作り直す（既定） | 2字以上の VFM のグループは固定。残りの字だけで分類し、判定条件を満たせば固定したグループに加わることもある（固定したグループどうしは合わない） |
| すべて作り直す | VFM のグループは使わない |
| VFM のグループをそのまま使う | VFM のグループ（1字も含む）を固定し、VFM に無い字だけで分類 |

**カーニング**（「4 生成」の「VFM のカーニング」）

- **構成が変わったところだけ生成する（既定）**：VFM のグループを引き継いだグループ（VFM の構成員がちょうど1つの VFM グループで、ほかは VFM に無かった字）どうしの組は、VFM の値をそのまま残します。クラスの値は VFM の構成員どうしの値の最頻値、それと違う構成員の値は個別の値として残します。残した値には微小値の省略や接触回避の引き上げをかけません。手で入れた値はそれより優先します。ペアの詳細では理由が「VFM の値」になります。
- **すべて生成し直す**：VFM の値は使いません。

**書き出し**：VFM を読み込んでいるときは、その VFM を書き換えます（ボタンは「読み込んだ VFM を書き換えて保存」、ファイル名も同じ）。選んだマスターのペアのうち、対象の字どうしのペアだけを結果に差し替え、対象外の字を含むペア・メトリクス・ほかのマスターはそのまま残します。

確認（FOT-マティス ProN M の OTF と VFM、5,075 ペア）：対象 304 字、推定グループは先頭 216・後ろ 209。既定の設定では先頭 181／235・後ろ 144／191 のグループを引き継ぎ、クラスの組 16,740 は VFM の値、9,645 は生成。書き戻した VFM で元のペアの 4,917 組（97%）が同じ値のまま残りました（変わった 93・消えた 65 は、構成が変わったグループのペア）。


## v0.5.5 お作法でまとめるグループ作成（既定オン）

「2 作成」の「グループの決め方」にある **お作法でまとめる**（既定オン）で、グループ作成が次の1本の流れになります。操作は「グループを作成」を押すだけで、今までと変わりません。

1. **お作法でまとめる**：アクセント・濁点付きの字は元の字へ（Unicode の分解。Œ は左が O・右が E のように左右別の表も）。欧文の元の字は定番の組（左側：B D E F H I K L M N P R／C G O Q／b h k l／m n p r／c d e o q／v w y／V W、右側：H I M N／D O Q／h m n／b o p／v w y／V W）。記号が出っ張る側（ホーン、ď ľ ť Ľ、濁点・半濁点の右）は分けます。
2. **輪郭で確かめる**：派生した字は、元の字にインクがある高さだけで比べます（記号の部分は比べない）。許容は判定条件の2倍、かなは6倍（濁音は少し描き直されていることが多いため）。元の字どうしは6倍で、明らかな外れだけを外します。
3. **形でまとめる**：残りの字と外した字は、今までの判定条件でまとめます。形の近い字はお作法のグループにも加わります（お作法のグループどうしは合わない）。

手で固定したグループと、読み込んだ VFM のグループが優先です。作成後は、まとめたグループの数、記号の側で分けた字の数、輪郭が違うため外した字（元の字つき）を表示します。「3 調整」のグループ一覧では、お作法のグループに「お作法」と出ます（記号を含むので、許容超えの警告は出さず参考値を表示）。作業JSON にスイッチの状態を保存し、古い作業JSON はオフで復元します。

**評価**（OFL 20書体の欧文、正解＝プロのカーニングで相手と値の並びが同じ字、Web 版のエンジンで測定。後ろ側 / 前側）

| | F1 | 適合率 | グループ数／プロ | 全字のグループ数 | プロが詰めるペアの値のずれ |
|---|---|---|---|---|---|
| お作法オフ（強さ0） | 0.087 / 0.043 | 92% / 87% | 4.05 / 3.87 | 4,495 / 5,141 | 0.7 |
| お作法オン（強さ0） | 0.767 / 0.703 | 88% / 90% | 1.33 / 1.49 | 1,618 / 2,086 | 1.4 |
| お作法オン（強さ40） | 0.780 / 0.746 | 85% / 86% | 0.93 / 1.09 | 1,049 / 1,461 | 3.1 |

かな（IBM Plex Sans JP）：後ろ側の適合率 100%、グループ 177 → 125。FOT-マティス ProN M の304字（欧文＋かな）：295×264 → 225×165 グループ、容量の概算 157.5 → 77.6 KiB。

あわせて、グリフ名を持たないフォント（CID など）でも、グリフ名を FontLab の名前（A、uni3042 …）で表示するようにしました。

## v0.6.6 設定の整理（共通・欧文・和文）
- 「4 生成」の設定を、上から「共通」「欧文」「和文」の順に並べ直しました。
  - 共通（常に表示）：大きく詰める組の強さ、欧文と和文を同じ基準で詰める。カスタムでは、共通の細かい設定（光学判定の比重・接触を防ぐ余白・そのまま使う値の範囲・微小値・許容差）と容量（グループの統合）。
  - 欧文（カスタム）：優先度で残す割合、学習した補正、数字の保護。
  - 和文（カスタム）：和文（かな）で残す割合、かなのくぼみ、字詰め。和文の約物は常に表示（いちばん下）。
- 「和文の詰める強さ」をなくし、「大きく詰める組の強さ」1本で欧文・和文の詰め具合を決めるようにしました（和文の強さは常に 100%）。書体によって欧文より弱いほうが合うもの（Noto Sans JP）と同じほうが合うもの（明朝体）があり、分ける根拠がはっきりしなかったためです。
- 「文字間隔（サイドベアリング）」は外しました（サイドベアリングは FontLab の Autospace で決めるため）。保存してあった値は 0 として扱います。
- 上限がなくなったので、「上限に張り付く組は0にする」も外しました。
